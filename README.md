# 竞品方案对比分析助手

> 语义匹配（BiEncoder）+ RAG（检索召回）+ 结构化生成（guided_json）·
> 把「企业 IT 采购方案对比」从原来人工查资料拼表格的 **4 小时**，压缩到 **15 分钟**
> 通用开源项目：场景不绑定任何厂商/产品，数据可替换，供企业 IT 售前 / 解决方案团队复用。

> **场景为通用表述**：本项目只做「企业 IT 采购方案对比」这一通用业务场景，不绑定任何厂商/产品，任何人可替换为自己的领域数据。

---

## 一、项目背景

### 痛点
做一次竞品方案对比，销售/售前要经历这几步**手工苦力活**：

1. 翻几十个文档、产品手册找双方参数（规格 / 性能 / 价格 / 生态 / 服务）；
2. 把信息一条条比对、理成一张对比表；
3. 写成优劣势分析和"赢单策略"。

这一步做下来，快的要 **半天，慢的要一整天**；而且：
- 信息零散、口径不一，同一个竞品不同销售说得各不一致；
- 新人不知道竞品怎么打，老手的经验传不下去；
- 竞品信息更新快，资料库永远是过时的。

### 目标
把「客户需求 → 竞品对比报告」做成**自动化流水线**：

| 流程 | 原来（人工） | 现在（本系统） | 提升 |
|------|------------|---------------|------|
| 竞品信息检索 | 翻文档/N 个网页 | RAG 语义检索 Top-K 召回 | — |
| 需求-竞品对齐 | 人肉判断哪个功能点能对标 | BiEncoder 语义匹配自动对齐 | — |
| 对比表生成 | 手工拼 Excel/表格 | 结构化生成（guided_json） | — |
| 整体耗时 | **4 小时** | **15 分钟** | **16 倍** |

> 上表为**设计值 / 目标值**，用真实演示脚本即可复现运行逻辑（见下方「本地演示」）。

## 二、技术架构

### 核心模块（职责单一、可替换）

```
┌─────────────────────────────────────────────────────────────────┐
│                       面向业务的一句话入口                       │
│          CompetitorComparisonAssistant.compare(需求)            │
└──────────────────────────────┬──────────────────────────────────┘
                               │
       ┌───────────┬───────────┴────────────┬────────────┐
       ▼           ▼                        ▼            ▼
┌────────────┐ ┌──────────┐ ┌───────────────┐ ┌───────────┐
│ 检索模块    │ │ 匹配模块  │ │ 结构化生成模块  │ │ 对比编排    │
│ retrieval  │ │ matching │ │ generation    │ │ orchestr.  │
│ · 向量索引   │ │ · 语义打分│ │ · 单元格结论    │ │ · top-K排序 │
│ · Top-K召回 │ │ · 阈值命中│ │ · 赢单策略总评  │ │ · 逐竞品跑  │
└────────────┘ └──────────┘ └───────────────┘ └───────────┘
```

### 技术选型

| 模块 | 技术 | 本仓库做法 | 生产可替换为 |
|------|------|-----------|-------------|
| 知识库存储 | 结构化数据 + 文档 RAG | 内存向量索引（`VectorIndex`） | FAISS / Milvus + 文档分块索引 |
| 需求→能力对齐 | 文本匹配（BiEncoder） | `MockBiEncoder`（确定性词典语义打分） | sentence-transformers 真实 embedding |
| 对比表生成 | LLM + 结构化输出 | `MockStructuredGenerator`（guided_json 契约） | 真实 LLM + JSON Schema 约束解码 |
| 对比编排 | 流水线编排 | `ComparisonPipeline` | 不变 |

### 三个刻意保留的设计点
1. **换后端零改动**：检索/匹配/编排只依赖「`encode(text)->vec`」和「`compare_cell(...)->dict`」这两个接口，Mock 层改真实现，上层一行不改；
2. **结论来源解耦**：`结论` 来自独立的**领域竞争定位模型**（销售沉淀），`语义相似度` 只负责召回对齐和**佐证**——避免「相似度高低」被误当「强弱」这种明显错误归因；
3. **结构化输出契约**：`CELL_SCHEMA` 显式定义对比单元格的 JSON Schema，约束结论枚举 `{我方优势, 势均力敌, 我方短板}`，为换真实 guided_json 提供稳定契约。

## 四、典型业务效果

销售打单做竞品对比，过去每单要翻几十个文档找参数、手工拼表，耗时 4 小时，且信息口径不一、新人无从下手。使用本助手：

- 输入客户需求，自动输出结构化对比报告 + 赢单策略，对比报告生成从 **4 小时降到 15 分钟**（16×）；
- 逐维度自动对标（定位 / 功能 / 性能 / 价格 / 生态 / 服务 6 类），跨文档信息口径统一；
- 能力点向量索引 + 结构化维度描述双路召回，BiEncoder 语义匹配实现「客户需求 → 竞品能力点」自动对齐；
- 结论来自独立的领域竞争定位模型，与语义相似度解耦，避免「描述相似 = 强弱相当」的错误归因；
- 全程离线可跑，pytest **19 个单测全过**，可直接集成到销售 / 售前流程。

## 五、设计问答（FAQ）

**Q1：这个项目里 similarity 和结论是什么关系？**
A：相似度用于**检索召回与对齐**（判断"哪个竞品能力点能对上这条需求"），并作为**佐证证据**写进报告；**对比强弱结论**来自独立的领域竞争定位模型（销售沉淀的"我方在该维度相对该竞品是强是弱"）。这样避免了一个常见错误归因——把"两边描述很像"当成"我方要输"。

**Q2：为什么用 Mock 而不是真实 LLM/向量库？**
A：为了**可离线、可复现、秒级跑通单测**，保证项目任何时候都能离线演示。Mock 只替换两个最小接口（编码器、单元格生成器），检索/匹配/编排逻辑与真实实现完全一致，换真后端上层零改动——这也正好是"生产可替换性"的证据。

**Q3：语义命中阈值怎么定的？高了低了会怎样？**
A：`SEMANTIC_THRESHOLD=0.55`。太高会漏召回（客户需求对不上任何能力点，报告变空），太低会误召回（把无关能力点塞进报告）。它只影响"对齐"，不影响结论分档。

**Q4：维度要加一个怎么做到不侵入？**
A：维度与结构解耦。加一个维度 = 在 `our_spec` / 竞品 `spec` / `positioning` 里补一条数据，模型层自动纳入生成，无需改 `generation/orchestrator`。

**Q5：这个系统在 to B 交付里真实的难点在哪？**
A：不在算法，在**领域知识沉淀**——竞争定位模型(`positioning`)需要销售/售前持续维护；以及**知识库时效**——竞品更新参数后要能增量回流。本项目把结论与检索解耦，正是为了让领域维护成本可控。

## 快速上手

### 0) 环境
```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -e ".[dev]"     # 运行时零第三方依赖，dev 仅需 pytest
```

### 1) 本地演示（离线跑通，无需 API Key，约 1 秒）
```bash
cd src && python -m competitor_comparison.demo
```

### 2) 跑单测
```bash
python -m pytest            # 19 passed
```

### 3) Python 里用
```python
from competitor_comparison import CompetitorComparisonAssistant
from competitor_comparison.sample_data import OUR_SPEC, SAMPLE_COMPETITORS

assistant = CompetitorComparisonAssistant(OUR_SPEC, SAMPLE_COMPETITORS)
reports = assistant.compare("客户要求国产化、自主可控、本地化部署", top_competitors=2)
for r in reports:
    print(r.competitor_name, r.summary)
```
